# xkey Static Password Management

YubiKey-style static password management for xkey. Passwords are stored as individual JSON files via the `storage.Backend` interface (file-based by default), with each entry persisted at `staticpw/{id}.json`.

## Access Modes

The password store supports two access control strategies for decryption:

### Mode A: PIN-Per-Operation (`pin_per_operation`)

Every decryption requires the user PIN. The `PINAccessStore` wraps the `EncryptedStore` and calls `PINManager.VerifyUserPIN()` before each `GetDecrypted` call.

- Non-decrypting operations (Add, List, Delete) proceed without PIN verification.
- Best for high-security environments where each password reveal must be authenticated.

```go
store, _ := staticpw.NewPINAccessStore(encryptedStore, pinManager)
pw, err := store.GetDecrypted("DatabaseProd", userPIN) // PIN required every time
```

### Mode B: Session-Based (`session_based`)

A single `Unlock(pin)` call transitions the `SessionStore` to the unlocked state. All `GetDecrypted` calls succeed without additional PIN prompts until `Lock()` is called.

- `Unlock(pin)` verifies the user PIN and enables decryption.
- `Lock()` transitions back to locked state.
- `IsLocked()` reports current state.
- Best for interactive sessions where repeated PIN entry is impractical.

```go
store, _ := staticpw.NewSessionStore(encryptedStore, pinManager)
store.Unlock(userPIN) // One-time PIN verification
pw, _ := store.GetDecrypted("DatabaseProd") // No PIN needed while unlocked
store.Lock()
```

## Encryption Model

The `EncryptedStore` wraps any `Store` implementation and transparently encrypts the password field using a `types.SymmetricEncrypter`. The encrypter is provided by the active backend (software AES-GCM, TPM2 symmetric, PKCS#11, cloud KMS, etc.).

Encrypted passwords are stored as `ENC:<base64(json(EncryptedData)))>`. The `EncryptedStore` prevents double-encryption and supports backward-compatible reads of plaintext entries.

```
Write:  plaintext --> SymmetricEncrypter.Encrypt() --> "ENC:..." --> storage
Read:   storage --> "ENC:..." --> SymmetricEncrypter.Decrypt() --> plaintext
```

Migration from plaintext to encrypted storage is handled by `EncryptedStore.MigrateToEncrypted()`, which re-writes all plaintext entries in place.

## Auto-Unseal via PlatformStore

When PlatformStore is configured, the user PIN can be stored as a sealed secret under the well-known name `platform/user-pin`. On boot, the auto-unseal sequence retrieves the PIN from PlatformStore and unlocks the password store automatically. See [Auto-Unseal](auto-unseal.md) for the full boot sequence.

## Folder Organization

Passwords can be organized into hierarchical folders using the `FolderPath` field. Folder paths use forward-slash separators (e.g., `Work/Email`).

- **ID generation** includes folder path: `generateID(name, folderPath)` produces `"work/email/myserver"`.
- **ListByFolder** returns entries matching a specific folder path.
- **ListFolders** returns all unique folder paths (including parent segments derived from nested paths).
- **MoveToFolder** relocates an entry by deleting the old key, updating the path, and re-adding with a new ID.
- Read-only entries (auto-generated by TPM policy, etc.) cannot be moved, updated, or deleted.

## Storage Architecture

The static password store uses the same `storage.Backend` adapter pattern as FIDO2's `BackendStorage`. The `BackendStore` wraps any `storage.Backend` implementation, defaulting to file storage at `./data/staticpw`.

Because the barrier ALWAYS wraps the base backend, all password entries stored via `storage.Backend` are transparently encrypted with AES-256-GCM before reaching disk. When LUKS is also active, entries pass through two encryption layers (barrier + LUKS) before reaching the physical filesystem. The `EncryptedStore` may add a third layer by encrypting individual password fields with a symmetric encrypter.

Key behaviors:

- **Thread safety** -- All operations are protected by `sync.RWMutex`
- **ID generation** -- Deterministic, derived by lowercasing the entry name (and folder path)
- **Lookup** -- Exact ID match first, then case-insensitive name scan
- **Duplicate detection** -- Checked by both ID and name within the same folder
- **Ordering** -- List results sorted by name (case-insensitive)
- **Multi-tenant** -- Optional tenant isolation via `NewTenantStore(backend, tenantID)`

```
/var/lib/xkey/staticpw/
  staticpw/myserver.json
  staticpw/work/email/myserver.json
```

## CLI Commands

### `xkey password add`

Add a new static password.

```bash
xkey password add --name "MyServer" --password "s3cret"
xkey password add --name "MyServer" --generate
xkey password add --name "MyServer" --generate --length 64 --charset alphanumeric
xkey password add --name "MyServer" --generate --notes "SSH key for prod"
```

| Flag | Default | Description |
|------|---------|-------------|
| `--name` | (required) | Password name/identifier |
| `--password` | | The password to store |
| `--generate` | `false` | Generate a random password |
| `--length` | `32` | Generated password length (8-128) |
| `--charset` | `all` | Charset: `all`, `alphanumeric` |
| `--notes` | | Optional notes |
| `--store` | `./data/staticpw` | Password store path |

`--password` and `--generate` are mutually exclusive. One must be provided.

### `xkey password list`

List all stored passwords. Aliases: `ls`

```bash
xkey password list
xkey password list --show-passwords
```

| Flag | Default | Description |
|------|---------|-------------|
| `--show-passwords` | `false` | Show password values (masked by default) |
| `--store` | `./data/staticpw` | Password store path |

### `xkey password get`

Retrieve a password value. Aliases: `show`

```bash
xkey password get "MyServer"
xkey password get "MyServer" | xclip -selection clipboard
DB_PASS=$(xkey password get "MyServer")
```

Outputs the raw password to stdout with no trailing newline, suitable for piping.

| Flag | Default | Description |
|------|---------|-------------|
| `--store` | `./data/staticpw` | Password store path |

### `xkey password remove`

Remove one or more passwords. Aliases: `rm`, `delete`

```bash
xkey password remove "MyServer"
xkey password remove "Server1" "Server2" --force
```

| Flag | Default | Description |
|------|---------|-------------|
| `--force` | `false` | Skip confirmation prompt |
| `--store` | `./data/staticpw` | Password store path |

### `xkey password type`

Type a stored password via the virtual USB keyboard. Aliases: `emit`

```bash
xkey password type "MyServer"
xkey password type "MyServer" --socket /tmp/xkey.sock
```

The daemon types the password as USB keyboard input through the virtual HID
keyboard device. The keystrokes appear as physical keyboard input to the host OS.

Requires the xkey daemon to be running in FIDO2 mode (`xkey fido2`).

| Flag | Default | Description |
|------|---------|-------------|
| `--socket` | auto-detect | IPC socket path |

## Password Generation

Generated passwords use `crypto/rand.Int` for uniform distribution (no modulo bias).

| Charset | Characters |
|---------|-----------|
| `all` (default) | `a-z A-Z 0-9 !@#$%^&*()-_=+[]{}\|;:',.<>?/~\`` |
| `alphanumeric` | `a-z A-Z 0-9` |

Length range: 8--128 characters. Default: 32.

## Configuration

Configuration priority (highest to lowest):

1. CLI flags (`--store`)
2. Environment variables: `XKEY_PASSWORD_STORE`
3. Config file: `~/.config/xkey/config.yaml`

```yaml
password:
  store_path: /var/lib/xkey/staticpw
```

## Touch & Keyboard Emulation

Xkey supports YubiKey-style touch behavior: when the daemon has a pending
WebAuthn user presence request, running `xkey touch` approves it. When no
request is pending and a default password is configured, touch types the default
password via the virtual USB keyboard.

### `xkey touch`

```bash
# Approve pending WebAuthn request or type default password
xkey touch

# Type a specific named password
xkey touch --password "DatabaseProd"

# Custom socket path
xkey touch --socket /tmp/xkey.sock
```

| Flag | Default | Description |
|------|---------|-------------|
| `--password` | | Name of password to type |
| `--socket` | auto-detect | IPC socket path |

### Daemon Flags

The FIDO2 daemon (`xkey fido2`) accepts these flags for password and touch support:

| Flag | Env Var | Default | Description |
|------|---------|---------|-------------|
| `--password-store` | `XKEY_FIDO2_PASSWORD_STORE` | `/var/lib/xkey/staticpw` | Path to static password store |
| `--socket` | `XKEY_FIDO2_SOCKET` | `$XDG_RUNTIME_DIR/xkey/xkey.sock` | IPC socket path |
| `--default-password` | `XKEY_FIDO2_DEFAULT_PASSWORD` | (none) | Password name to type on bare touch |
| `--notify-command` | `XKEY_FIDO2_NOTIFY_COMMAND` | (none) | Custom notification command |

### Notifications

When a WebAuthn user presence request arrives, the daemon notifies the user:

1. **D-Bus** (default on Linux): Desktop notification via `org.freedesktop.Notifications`
2. **Custom command**: Override with `--notify-command`, supports template variables:
   - `%o` -- operation (register/authenticate)
   - `%r` -- relying party ID
   - `%n` -- relying party name
   - `%u` -- user name
3. **Log**: Always active as fallback via structured logging

Example with custom notification:
```bash
xkey fido2 --notify-command 'notify-send -u critical "Xkey" "Touch required: %n (%o)"'
```

### IPC Protocol

The daemon listens on a Unix domain socket (mode 0600). The `xkey touch` and
`xkey password type` commands communicate via JSON messages:

| Message | Action |
|---------|--------|
| `touch` | Approve pending UP, or type default password |
| `type_password` | Type a named password via virtual keyboard |
| `status` | Check daemon status |

### Virtual Keyboard

The virtual keyboard uses Linux UHID to create a USB Boot Protocol keyboard
device (vendor 0xF1D0, product 0x0004). Characters are typed as sequential
key-down/key-up HID reports with a 5ms inter-keystroke delay. Supports the
full US keyboard layout (printable ASCII).
